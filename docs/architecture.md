# OptiScale Vertical Slice 3 architecture

```text
loadgen → demo-api → inventory-service → PostgreSQL
             /metrics         /metrics + DB-query metrics
                      ↓ Kubernetes pod discovery
                   Prometheus
                      ↓ typed, timestamped observations
                 capacity analyzer
 HEALTHY / TARGET_SATURATED / DEPENDENCY_SATURATED /
          CAPACITY_BLOCKED / UNCERTAIN
                      ↓ deterministic policy and guardrails
           healthy-only advisory forecast (when enabled)
           Deployment /scale subresource (when useful)
                      ↓
         status.lastDecision + lastScaleDecision
```

## Services and telemetry

`demo-api` performs configurable local work and makes a bounded HTTP call to `inventory-service`. Inventory performs a real SQL query against the local PostgreSQL service. Each HTTP service exports request/error counters, in-flight request and local-work gauges, and a request-duration histogram. `demo-api` additionally exports `http_concurrency_slot_seconds_total`, which accumulates wall-clock time from successful semaphore acquisition until release, including both local work and downstream HTTP wait. Time waiting before acquisition is excluded and separately accumulated in `http_concurrency_queue_seconds_total`; current held slots and queue waiters are also gauges. The older `http_local_work_seconds_total` and `http_active_work` remain diagnostic signals, not the target capacity input. Inventory retains its existing averaged active-work gauge query. Inventory also exports application-observed database request/error counters, in-flight database requests, and a DB-query duration histogram. Prometheus discovers annotated pods dynamically in the demo namespace; neither service address nor a Minikube IP is embedded in scrape configuration. The DB active-query gauge includes calls waiting on a database connection and calls executing queries; it is not a claim about PostgreSQL CPU or internal wait states.

The OptiScaler observes aggregate target slot occupancy with `sum(rate(http_concurrency_slot_seconds_total{...}[1m]))`, hottest per-instance occupancy from the same 1-minute slot rate filtered to instances above 1 RPS in the 30-second request window, and effective serving replicas with `count(sum by(instance) (rate(http_requests_total{...}[30s])) > 1)`. Effective serving replicas therefore means instances recently above the sample's meaningful-traffic cutoff (>1 RPS); the controller validates that the result is an integer between zero and the Kubernetes Ready count. Kubernetes readiness is necessary but not sufficient evidence of realized application capacity. For example, Ready=3 and effective=2 means current learned safe capacity is credited to two serving replicas only. Connection reuse at the Service level can plausibly direct little traffic to a newly Ready endpoint; this is a plausible mechanism, not established cause. If Ready exceeds effective, capacity learning is suspended and target scale actions are held until the new serving capacity materializes.

The target's `physicalConcurrencyLimit: 20` is the actual per-pod semaphore capacity (`DEMO_CONCURRENCY=20`). With the existing `safeCapacityMargin: 0.75`, the derived safe operating occupancy is 15 slots per serving replica; the physical limit is not confused with that lower safe boundary. For each eligible healthy sample, throughput efficiency is `successful RPS / aggregate held-slot occupancy`. The conservative learned efficiency is extrapolated to 20 physical slots to estimate physical per-replica throughput, then multiplied by 0.75 once to derive safe throughput per serving replica. Realized current safe capacity is safe per-serving-replica throughput multiplied by effective serving replicas. Learning requires Ready replicas to match requested replicas and effective serving replicas, positive aggregate occupancy, mean occupancy per effective replica at least 30% of the safe boundary (4.5 slots) and hottest occupancy below the safe boundary. This is an empirical linear extrapolation, not a queueing model. Each dependency retains its own latency and utilization queries/thresholds; inventory still uses averaged `http_active_work`. Request and error rates use `rate()` over monotonically increasing counters. The controller retains total requests per second, derives successful requests per second as total minus errors, and derives error ratio as error RPS divided by total RPS. Missing, malformed, non-finite, stale, or future-dated observations stay absent rather than becoming zero.

Signal roles are intentionally separate: p95/SLO asks whether users are suffering; local active-work telemetry indicates component constraint; request/successful-request rates quantify served demand; and error ratio describes failure rate and whether that reliability observation is trustworthy. Request/error telemetry is recorded in the latest DecisionRecord for capacity analysis, not used as a scaling trigger in this slice.

## Analyzer rules

- `UNCERTAIN`: required telemetry or configuration evidence is invalid/incomplete, multiple independent dependencies qualify, or an upstream component has independent utilization saturation alongside a saturated downstream dependency.
- `HEALTHY`: the target p95 is at or below its SLO. Dependency activity alone does not trigger scaling while the target SLO is satisfied.
- `TARGET_SATURATED`: target p95 exceeds its SLO and the hottest traffic-bearing target replica's held-slot occupancy is at or above the derived safe operating boundary. Aggregate/Ready averaging cannot conceal a hot serving pod. This target signal takes priority over dependency latency signals.
- `DEPENDENCY_SATURATED`: target p95 exceeds its SLO, hottest target slot occupancy is below its safe boundary, and one configured dependency crosses its latency or utilization threshold.
- `CAPACITY_BLOCKED`: target p95 exceeds its SLO, target is not locally saturated, and a root dependency marked non-scalable crosses a configured latency or active-query threshold. A component declared as depending on that root is not selected solely because its request latency also rose; independent utilization saturation remains ambiguous. Evidence identifies which thresholds fired, the non-scalable configuration, target held-slot occupancy, and upstream topology.

The analyzer emits classification, component, evidence, reason, and a qualitative confidence level based on evidence completeness. These rules describe co-observed metrics only; they do not establish causality.

## Policy and Kubernetes writes

Target saturation selects the target Deployment; dependency saturation selects that dependency only when `scalable: true`. A verified non-scalable root bottleneck produces `CAPACITY_BLOCKED` and `HOLD`, preserving current replicas and listing `SCALE_TARGET` and `SCALE_DEPENDENCY` as rejected actions with reasons. This prevents adding API or inventory replicas when the measured database dependency is the bottleneck. Healthy evidence holds; uncertain evidence or invalid bounds enters `PROTECTED_MODE`. Upward changes use the configured max step and per-workload maximum; configured minimums are retained as safety bounds. Cooldown applies across target and dependency changes. A no-op decision never writes.

The controller supports `apps/v1 Deployment` only. It reads and updates `autoscaling/v1.Scale` through `deployments/scale`; it does not directly mutate `Deployment.spec.replicas`. RBAC is namespace-scoped and includes `deployments/scale` access plus `get/list/watch` on target-namespace Pods and ReplicaSets for readiness and revision observation. Target observation requires the aggregate slot-occupancy, hottest-instance occupancy, serving-replica-count queries, and physical concurrency ceiling; missing/invalid required observations fail safely.

## Predictive prescaling

Prediction is optional (`spec.prediction.enabled`) and advisory. The existing analyzer and reactive policy run first. Forecasting can replace only a healthy `HOLD`; `TARGET_SATURATED`, dependency saturation, `CAPACITY_BLOCKED`, uncertain/protected telemetry, and cooldown retain precedence. Prediction never scales down and uses the existing target bounds, `maxScaleUpStep`, cooldown, `/scale`, status, and event path. A max-replica no-op remains `HOLD`.

Stable request/error/success observations retain their configured 1-minute semantics for status, error ratios, dependency observations, and healthy capacity samples. Target forecasting has a distinct `predictiveRequestRateQuery`; the sample uses `sum(rate(http_requests_total{namespace="optiscale-demo",app="demo-api"}[30s]))`. `prediction.predictiveDemandWindowSeconds` is explicitly configured to `30` to match that query. The controller does not parse the PromQL range or substitute stable request rate if predictive telemetry is missing, stale, or non-finite. Missing predictive telemetry suppresses prescaling only; healthy capacity learning continues to use stable successful RPS and aggregate constrained-slot occupancy.

The controller retains a bounded in-memory predictive-demand series per OptiScaler: at most 20 observations within five minutes. This retention history is distinct from the fixed 120-second trend-fit window: ordinary least-squares regression uses only trailing samples at or after `latest sample timestamp - 120s`, with elapsed seconds as x and requests/second as y. The cutoff is anchored to the latest sample, not wall-clock time. The recent fit intentionally emphasizes the current sustained demand regime, but does not relax quality or safety gates. A candidate requires at least five fit points spanning 60 seconds, a latest point no older than 45 seconds, no inter-sample gap above 45 seconds, a planning horizon no longer than the fit span, a finite positive slope, and a finite nonnegative forecast at that planning horizon. Fit quality is `HIGH` only when R^2 >= 0.95 and normalized RMSE (RMSE divided by observed rate range) <= 0.10. `MEDIUM` is R^2 >= 0.85 and normalized RMSE <= 0.20; only `HIGH` may trigger prescaling. Flat/falling, sparse, stale, gapped, non-finite, or poorly fitting fit-window data is rejected. Capacity learning continues to use its existing retained history and is unchanged by this trend-fit window.

Healthy capacity samples use successful RPS divided by aggregate target held-slot occupancy as observed throughput efficiency (successful requests/s per occupied-slot equivalent). A sample is learnable only when target latency remains within SLO, all configured dependencies are below their thresholds, request/success/error and aggregate/hottest occupancy observations are fresh and complete, target error ratio is at or below `spec.prediction.maxErrorRate`, requested replicas equal Kubernetes Ready replicas and effective serving replicas, and mean occupancy per effective serving replica is at least 30% of the derived safe occupancy but below it, with the hottest replica also below the safe boundary. For the sample's physical limit of 20 and margin 0.75, safe occupancy is 15 and the learning floor is 4.5 per effective serving replica. Capacity learning is disabled while any Ready replica has not demonstrated meaningful request traffic. At least three capacity samples are required. The controller takes the nearest-rank 20th percentile of healthy throughput efficiencies, multiplies it by the physical slot limit to estimate throughput at the physical ceiling, then applies `spec.prediction.safeCapacityMargin` once. Realized current safe capacity multiplies safe per-serving-replica throughput by effective serving replica count. This is an intentionally simple linear empirical extrapolation, not a claim to infer queueing dynamics. The sample sets margin `0.75` and maximum learning error ratio `0.02`.

The predictive-demand observation lag is derived as half the configured rate window (`predictiveDemandWindowSeconds / 2`); for the sample's 30-second rate window it is 15 seconds. The predictive planning horizon is `readiness lead + reconcile interval + predictive-demand observation lag`. Fresh readiness samples use `PodReady=True.lastTransitionTime - metadata.creationTimestamp` only for Ready, non-terminating pods owned by the current target ReplicaSet, with valid ordered timestamps and `restartCount=0` for every regular container. A restart in any regular container invalidates that pod as a startup sample; init-container restart history is ignored. Every currently Ready non-terminating selected pod still counts toward Ready replicas, including restarted pods.

The current revision identity is Kubernetes' `pod-template-hash` from the unique Deployment-owned ReplicaSet whose pod template matches the Deployment's current template, after removing that hash label for the comparison. The Deployment generation must be observed; missing, multiple, or mismatched revision evidence during rollout is treated as ambiguous and blocks prescaling. The largest eligible fresh lead is persisted directly in status as `learnedReadinessLeadTimeSeconds`, `learnedReadinessObservedAt`, and `learnedReadinessTemplateIdentity`. If no current-revision fresh sample exists, that persisted value is reused only when its template identity matches the currently resolved revision. DecisionRecord identifies `CURRENT_FRESH_SAMPLE` versus `PERSISTED_LEARNED_SAMPLE`; `readinessLeadTimeSeconds` remains the raw creation-to-Ready duration, while `controlLoopAllowanceSeconds` and `demandObservationLagSeconds` remain separate. For example, 22 seconds measured readiness + 15 seconds control-loop allowance + 15 seconds observation lag gives a 52-second planning horizon. Missing readiness or predictive-demand evidence suppresses prescaling; a fallback forecast used to report trend quality is never used for a scale decision. This does not measure end-to-end `/scale`-to-Pod-creation latency: Kubernetes scheduling and Deployment-controller delay are not yet learned or added as an invented constant, and measuring that interval is future work. In-memory demand and capacity histories reset on controller restart and are not durable or shared between controller instances; persistent forecast history and multi-controller coordination are future work.

### Capacity realization and runtime proofs

Kubernetes Ready count is not treated as realized application capacity: `effectiveServingReplicas` is derived from recent per-instance request traffic, and current safe capacity credits only those traffic-bearing replicas. The success profile (`predictable-ramp-success.ps1`) uses moderate periodic connection turnover and, on 2026-09-12, demonstrated a healthy `PRESCALE_TARGET` from 2 to 3, with the third replica both Ready and traffic-bearing before the SLO boundary. The latest measured run completed 104,796 k6 requests with 0 dropped iterations, 0 HTTP failures, and 101.52ms overall p95; the README records the decision-time forecast and capacity evidence. The original `predictable-ramp.ps1` remains a complementary guardrail scenario: long-lived connection reuse or traffic distribution can plausibly leave a Ready endpoint with little recent traffic, in which case OptiScale holds further target scaling until capacity is observed serving. That profile exercises capacity realization and may cross the SLO; it is not the SLO-preservation proof. Neither scenario establishes a universal production traffic-distribution pattern.

## Status and explainability

`status.lastDecision` records SLO target, observed target p95, stable target request/successful-request rates and error ratio when defined, compact per-dependency request/error summaries, bottleneck classification/component, requested and Ready replicas, effective serving replicas, aggregate and hottest held-slot occupancy, physical and safe occupancy boundaries, realized safe capacity, and—when enabled—the observed fast `predictiveRequestRate`, its configured window and derived lag, forecast demand and full planning horizon, slope, fit quality, safe capacity, raw measured readiness lead and evidence source, target template identity, control-loop allowance, prediction acceptance/rejection, evidence, qualitative confidence, chosen action/workload, rejected alternatives, current/desired replicas, and reason. The latest learned readiness value, observation timestamp, and template identity are persisted independently at the OptiScaler status root; `lastDecision` is not used as its datastore. `status.lastScaleDecision` changes only after a real `/scale` mutation, so later HOLD or protected evaluations do not erase the most recent scaling rationale. One structured controller log is emitted per capacity evaluation with target, p95, SLO, requested/Ready/effective-serving replicas, occupancy, bottleneck, action, workload, and reason.

## Scope boundary

This slice does not implement Random Forests, arbitrary dependency graphs, persistent capacity learning, policy replay, PostgreSQL-internal telemetry, OpenTelemetry, Karpenter, or causal inference. Grafana is a local visualization layer only; it does not provide controller inputs or change policy. PostgreSQL is a real local workload; its deterministic delay uses a real SQL `pg_sleep` call, and observed query metrics describe application behavior rather than database internals. The configured P0 dependency list and deterministic rules are a demonstration, not a general optimizer.
